# runmanager: build contract

The shared contract for every worker building the Run manager's research path (plan-run-manager.md, Milestones 2 to 5). The spec owns the design: `~/Documents/obsidian/cerebral-swamp-vault/Projects/Script Asst/run-manager/spec-run-manager.md`. This file fixes what the spec leaves to the build: the command line, the test-case format, and the readings listed in section 4. Where this file and the spec disagree, the spec wins. Report the disagreement.

## 1. The command line

Launcher: `bin/runmanager`, the same form as `bin/editguard` (puts `lib/` on `PYTHONPATH`, runs `python3 -m runmanager "$@"`). Standard library only. Python 3.12.

| Command | Arguments |
| --- | --- |
| `init` | `--project P` |
| `status` | `--project P` |
| `start` | `--project P --kind research --run-number N` |
| `mark` | `--project P [--stopped]` |
| `act` | `--project P` |
| `close` | `--project P` |
| `recover` | `--project P` |
| `abandon` | `--project P` |

1. `P` is the project folder. Every other path is fixed by the spec and the run state: `P/.runs/run-state.json`, `P/.runs/{run-id}/snapshot/`, `requests.json`, `fingerprints.json`, `outcomes.json`, `flags-{N}.json`; run logs in `P/Runs/`.
2. **Exit codes:** 0 when the step ran. 1 for a refusal or a bad input, with one plain line on stderr. 2 for bad arguments (argparse's default).
3. **The clock:** every command reads the current time from the environment variable `RUNMANAGER_NOW`, format `YYYY-MM-DD HH:MM`, when it is set, and from the system clock otherwise. The run id is `run-YYYY-MM-DD-HHmm-{kind}`, from the start time.
4. **Output:** `start` prints `run_id: {id}` and `requests: {count}` on stdout, one per line. `status` prints `no open run`, or `open run: {id} ({kind}), step: {step}, next: {what comes next}`. Other commands may print a short summary. Tests check only exit codes and stderr text, never stdout, except `start`'s `run_id:` line, and a `run` step's `stdout` check (section 2, added 2026-10-26), which case 232 uses for `abandon` printing a log it couldn't write (section 6 item 4).
5. **Link lines and log links** use the project folder's own name: `[[Projects/{folder name}/{path without .md}|{file name without .md}]]`. The Edit guard reads link lines in that form (`lib/editguard/rules_research.py`, `link_line_target`). A link line is the request's indent plus four spaces, then `- [AGENT] [[…]]`.

## 2. The test-case format

Cases live in `lib/runmanager/tests/cases/{NN-short-name}/`. The runner is `lib/runmanager/tests/test_cases.py`, one pytest test per case folder.

```
{case}/
├── case.json          what the case tests, and which spec items, in plain words
├── before/            the project folder before the first step, any files, .runs/ included
├── files/             files the steps copy in (prepared outcomes, simulated stray edits)
├── steps.json         the steps, in order
└── expected/
    ├── tree/          the project folder after the last step (see "Comparing")
    └── log.json       optional: what the run log must hold
```

The runner copies `before/` to a temp folder named after the project (the project folder's name is `before`'s single top-level folder, such as `Lighthouse`, so `before/Lighthouse/…`). Then it runs each step.

**Steps** (`steps.json` is a list; each step is one object):

| Step | What the runner does |
| --- | --- |
| `{"run": ["start", "--kind", "research", "--run-number", "2"], "now": "2026-10-10 16:00", "exit": 0, "stderr": "text"}` | runs `bin/runmanager` with `--project {temp project}` added after the subcommand, with `RUNMANAGER_NOW` set to `now`. Checks the exit code. `stderr`, if given, must appear in stderr. `now` is optional and carries over to later steps once set |
| `{"copy": "files/outcomes.json", "to": ".runs/{run_id}/outcomes.json"}` | copies a file from the case into the project. `{run_id}` is the id the last `start` printed. A folder copies whole, overwriting |
| `{"delete": "Ideas/idea-x.md"}` | deletes a file in the project (to simulate an agent removing a note) |
| `{"editguard": true, "exit": 0}` | runs the real `bin/editguard check` with the open run's kind and the paths read from the open run in `run-state.json` (on a migration run: every `.runs/units/{run_id}-b*.json`, the run state, and the run id; on its second check, also `--judged flags-{first_check}.json --findings findings-flags.json` when `findings-flags.json` exists), and `--out .runs/{run_id}/flags-{next_check}.json`. Exit defaults to 0 |
| `{"flags": "files/flags-1.json"}` | instead of running the Edit guard, copies a prepared flags file to `.runs/{run_id}/flags-{next_check}.json`. Use it only when the real Edit guard can't produce the needed flag |
| `{"chmod": "Ideas", "mode": "555"}` | sets a file's or folder's mode in the project, `mode` an octal string. Added 2026-10-26 for Milestone 18: a read-only folder makes a command fail partway (notes are swapped in through a temp file beside them, so a read-only note alone doesn't stop a write). A later `chmod` step can give the mode back. After the last step, pass or fail, the runner gives the owner read and write on every file and read, write, and search on every folder, so the temp folder can be deleted |

A `run` step may also hold `"stdout"`: a string or a list of strings, each of which must appear in stdout (added 2026-10-26, for `abandon` printing its log when it can't be written, spec 09.3 item 3). Every other `run` step checks no stdout, as section 1 item 4 says.

**Comparing:** after the last step, the runner compares the temp project with `expected/tree/{project}/`:

1. Every file outside `.runs/` and `Runs/` must match byte for byte, and no file may be missing or extra.
2. `.runs/run-state.json` is compared as parsed JSON.
3. Under `.runs/{run-id}/`, only `snapshot/`, `requests.json`, `fingerprints.json`, `batches.json`, every `verify-*.json`, every `flags-*.json`, `findings-flags.json`, `undo-misses.json`, `pointer-misses.json`, `restore-misses.json`, and `removed/` are compared, and each `.runs/units/*.json` that `expected/tree/` holds, and only when `expected/tree/` holds them. Other files there are the code's working files and are ignored. A run folder in `expected/tree/` holding a `snapshot/` means it must exist; a `.runs/{run-id}/NO-SNAPSHOT` marker file in `expected/tree/` means that run's `snapshot/` must be gone.
4. `Runs/` is never compared byte for byte. `expected/log.json` checks the run logs:

```json
{ "file": "Runs/run-2026-10-10-1600-research.md",
  "first_line": "Research run 2, started 2026-10-10 16:00.",
  "sections": [ { "heading": "Requests still open",
                  "contains": ["- [r] What did a keeper earn in 1950?", "research-keeper-wages"] } ],
  "absent": ["Closes undone", "Still flagged after the second check"],
  "contains": [],
  "nothing_needs_you": false }
```

`first_line` is the first non-blank line after the frontmatter. The frontmatter must have `run-log` first in `type`. `sections` must appear as `## ` headings in the listed order, each holding every `contains` string. `absent` headings must not appear. `nothing_needs_you` true means the body's first line after `first_line` is "Nothing needs you." Several logs: make `log.json` a list.

Added 2026-10-26 for Milestone 18: `second_line`, if given, must equal the second non-blank line of the body. In a `sections` entry, `lacks` lists strings that must not appear in that section, and `"ordered": true` means the `contains` strings must appear in the listed order, each found after the one before it, so a repeated string can be checked once per entry.

**The section headings are fixed**, from spec 06.1 item 2: `## Requests still open`, `## Closes undone`, `## Notes changed outside the run`, `## Done`, `## Still flagged after the second check`.

## 3. Who writes what

1. Test cases and `expected/` are written from the spec and this contract alone, by a worker who never writes the code.
2. The code worker makes the cases pass and never edits a case. If a case looks wrong, it reports the case and the spec item, and leaves it failing.
3. The runner (`test_cases.py`) is written by the skeleton worker from section 2.

## 5. The migration path

Added 2026-10-12 for plan-run-manager.md Milestones 8 to 12. The spec sections are spec-run-manager.md 04 items 4, 5, 9, 16, and 20 to 22; 07.1; 07.2. Sections 1 to 3 above still hold.

### 5.1 The command line

| Command | Arguments |
| --- | --- |
| `start` | `--project P --kind migration [--request TEXT]` |

1. `start --kind migration` prints `run_id: {id}` and `batches: {count}` on stdout, one per line. The run id ends in `-migration`.
2. The typed request is saved as the open run's `request`, or `null` when none was typed.
3. The open run of a migration run: `id`, `kind` `"migration"`, `run_number` `null`, `request`, `step` `"migrating"`, `next_check` `null`, `started`, `batch` `1`, `round` `0`. A research run's open run has no `batch` or `round` key (spec 04 item 16).
4. `start` creates `.runs/units/` if it isn't there, and writes `.runs/{run-id}/batches.json` (spec 04 item 21), the snapshot copies of every story note, and `fingerprints.json` for every other covered note (spec 04 item 9).
5. With no new work, `start` exits 1 with "No new work since the last migration run." and claims nothing: no open run, no run folder. A run whose only finds are skipped pointer lines has no new work.
6. `status` on a migration run at `migrating` prints `next: run the migrator on batch {batch}, round {round}, then record`.

### 5.2 Readings for the scan

Claude's readings, 2026-10-12, made while briefing Milestone 8. They go to the writer with the case writer's own gaps.

1. **A story note** is a covered `.md` note (the same folders as section 4 item 9 and spec 04 item 9) whose frontmatter `type` list holds `brain-dump`, `idea-note`, or `area-note`, in any position (migrator-rules.md 01.8). A note with no frontmatter, or whose `type` list holds none of the three, is not a story note: it is fingerprinted, never scanned.
2. **A tagged bullet** is a list item (`-`, `*`, `+`, or `1.`, any indent, with or without a checkbox) that holds a status tag, `#status/` followed by a word. A bullet that holds an inline `%% … %%` comment is a trigger line too.
3. **A comment** is a block that starts on a line whose text, after any indent, begins with `%%`, and runs to the line that closes it with `%%` (often the same line). Its `text` is the whole block, line breaks kept as `\n`, indent included. Its `line` is the block's first line. A comment is a trigger line wherever it sits (spec 11 item 73).
4. **Frontmatter is never scanned.** Line numbers count every line of the file from 1, frontmatter included, as in the unit record.
5. **Lines the scan skips** (spec 07.1 item 5): a bullet whose checkbox is `[r]` or `[b]`; a `[x]` bullet holding a `#research/run-` tag; a bullet whose text after the marker and any checkbox starts with `[AGENT] `; and a comment starting on the line directly below any of these. A `%% [AGENT] … %%` comment is a comment, not an `[AGENT]` bullet, so the scan doesn't skip it: the request comment `close` writes (5.6 item 10) is a trigger line for the next run (spec 07.1 item 5; spec 11 item 96).
6. **Matching is by exact text, note by note, counting repeats** (spec 04 item 20). The whole line, indent included, with a tagged line's link targets left out (item 14) and a comment's read as item 15 says. If a note holds a text twice and the handled list holds it once for that note, the occurrence that comes first in scan order (item 10) is handled and the later one is new work. In a Brain Dump doc that is the one under the older date, so a line the writer re-adds under a newer date is the new one. Each entry matches one line. Within a note, exact text is matched before link targets are left out, so a line keeps the entry that reads as it does. Every story note's lines are matched against their own entries before any line is compared with the entries whose note no longer exists (item 16; added 2026-10-25, spec 11 item 104).
7. **A pointer** is `[migrated-to:: …]` at the end of a line. Its destinations are the wikilinks inside it, each turned into a path inside the project: drop the `Projects/{project folder name}/` prefix and add `.md`.
8. **A tagged bullet with a pointer that isn't matched by text** (spec 07.1 item 4): look for handled entries in the same note with the same set of destinations whose `text` no longer appears in the note. If exactly one, compare the status tags of the two lines. Each handled entry is used at most once: lines are taken in scan order, and a later line whose only candidate was already used by an earlier one is new work. An entry is used when a line is matched to it, whether that line is skipped or is new work because its tag changed. An entry item 6 matched is used too, and is no candidate (added 2026-10-25: case 204, where a moved folder rewrote two pointers to one note, and the line matched with link targets left out leaves the other its one candidate). Same tags: the line is skipped and goes in `skipped`, with `was` the entry's text. Different tags: new work. No such entry, or more than one: new work.
9. **Pieces.** In a Brain Dump doc, a date heading is a heading of any level whose text is exactly `YYYY-MM-DD`. A piece runs from its date heading to the next date heading or the end of the note. Lines above the first date heading form a piece with `heading` `null`. Any other story note is one piece with `heading` `null`. Only pieces with new trigger lines go into batches.
10. **Scan order** (spec 07.2 item 3): Brain Dump docs first, by path; inside each, the piece with `heading` `null` first, then date headings oldest date first, whatever order the note holds them in. Then the other story notes, by path. Inside a piece, `lines` follow the note's order.
11. **A piece's size** (spec 07.2 item 1): its new tagged bullets. A piece holding a new comment counts every bullet in it, new or not, except the lines the scan skips (item 5). An inline `%%` comment on a bullet makes that bullet one trigger line; it doesn't make its piece count every bullet.
12. **Cutting batches** (spec 07.2 item 1): take pieces in scan order. A piece joins the current batch if the batch stays at 20 or under; otherwise it starts a new batch. A piece over 20 is a batch of its own. Batches are `b1`, `b2`, … in order.
13. **Readings from the Milestone 8 case writer, 2026-10-12.** The open run of a migration run has `"run_number": null`, as `claim_run` already writes. `fingerprints.json` is written as `{}` when nothing is fingerprinted. `batches.json` always holds `"skipped"`, `[]` when empty. `heading` is the heading line as written, `#` marks included. A `start` that finds no new work leaves no run folder at all. `batches.json` always holds `"renamed"` too, `[]` when empty (added 2026-10-25, spec 04 item 21).
14. **A tagged line is compared with its link targets left out** (spec 07.1 item 10; spec 11 item 102). In every wikilink on the line, pointer or not, embeds included, the target, the part before `|`, is dropped; the shown text after `|` still counts. `[[Projects/Almond/Ideas/idea-almond|idea-almond]]` reads as `[[|idea-almond]]`, and a link with no `|` reads as `[[]]`. So a renamed story note, a moved project folder, or a link the writer pointed elsewhere keeps the line handled. A changed status tag, or a changed word outside the links, still makes it new work, or a skipped pointer line (item 8).
15. **A comment is compared by its exact text, with one allowance for renames** (spec 07.1 item 11; spec 11 item 103). Each link target is read as the path inside the project, with any `Projects/{folder}/` prefix dropped, whatever the folder is called; and an old path a rename the scan found (item 16) is read as its new one. A short link, a file name with no folder, follows a rename by its file name. The shown text, and every other word, is compared as written. So a comment the writer pointed at another story note that still exists is new work. Comments are compared through the renames after every tagged line is matched, so every rename item 16 finds counts.
16. **Carry-over and renames** (spec 07.1 item 12; spec 11 item 104). Lines no entry of their own note matched are compared, as items 14 and 15 say, with the entries whose `note` no longer exists in the project. Each such match is a rename from the entry's note to the line's. A Brain Dump line also gives one when its entry's `pointer` names, at some place in the list, a path that no longer exists, and the line's pointer names at that place a story note that does; the two lists must be the same length. `renamed` lists each rename once, `{"from", "to"}`, sorted by `from`, then `to`. `start` also writes `.runs/{run-id}/carried.json`, a working file the runner doesn't compare: each match whose entry's `text` or `note` differs from the line, as `{"entry": its place in the handled list, "was": its text, "note", "line", "text"}`, which `close` reads (5.6 item 4). The handled list doesn't change between `start` and `close`, so the place holds.

### 5.3 The batch cycle (Milestone 9)

Spec: spec-run-manager.md 04 items 6, 15, 22; 07.2 items 4 and 6; 08.1; 09.1 items 1, 2, 4, 5, 6. spec-migrator.md 05 (the record) and 09. spec-migration-verifier.md 03.1, 04.1, 05.1, 05.2, 06 items 1 to 4, 07 items 1, 3, 4.

| Command | Arguments |
| --- | --- |
| `record` | `--project P [--failed]` |
| `findings` | `--project P [--failed]` |

**Paths.** The batch's record file is `P/.runs/units/{run-id}-b{N}.json`. The cut-down record is `P/.runs/{run-id}/verify-b{N}-r{R}.json`. The findings file is `P/.runs/{run-id}/findings-b{N}-r{R}.json`. `N` is the open run's `batch`, `R` its `round`.

1. **`record`** (needs `migrating`) checks the record file's shape, then that every non-blank `copies` line of every unit it checks this round sits in its note, character for character, at a place the snapshot can't account for (spec-migrator.md 05.5 item 2; spec 11 item 81). A unit's copy missing from its note is a refusal like an invalid record, naming the unit, the note, and the line, so the session sends the migrator back to make record and note agree. So is a `migrate` source recorded as an edit left it (item 14), and a `migrate` copy into a note its source line's pointer already names, when an earlier run sent that line there for the same trigger (item 15). Valid: it saves a copy as `.runs/{run-id}/record-b{N}-r{R}.json`, writes the cut-down record, and moves to `verifying`. Missing or invalid: exit 1 with one line naming the file and what's wrong; nothing changes, so the session can retry the migrator.
2. **The shape check** (spec-migrator.md 05.2). A JSON object with the lists `units`, `left_in_place`, `questions`, `could_not`. Each unit has `id` (`u` and a number, unique in the file), `action` (`migrate`, `reject`, `edit`), `trigger` (`kind` `tag`, `comment`, or `request`; `text` a string), `sources` (at least one; each `note`, `line` ≥ 1, `text`), `copies` (each `note`, `under`, `lines`: at least one string; `creates_note` optional, true or false), `edits` (each `note`, `line`, `before`, `after`), `status` (`tentative`, `provisional`, `committed`, `rejected`), `status_from` (`tag`, `comment`, `parent tag`, `request`, `default`), and `why`. Every `note` is a relative path inside the project ending in `.md`, with no `..`. A `left_in_place` entry has `source` and `why`; `questions`, `source` and `ask`; `could_not`, `what` and an optional `source`. A `could_not` `source` may name a story note and no line, `{"note": …}` with no `line` or `text`: the migrator couldn't read that note (added 2026-10-25, spec 07.1 item 14).
3. **In a fix round** (`R` > 0) the record must also leave every unit that isn't being fixed exactly as it was in the last valid copy (spec-migrator.md 09 item 1). If it doesn't, `record` refuses as for an invalid record.
4. **The cut-down record** (spec-migration-verifier.md 03.1 item 1). Round 0: every unit handed to the check, each keeping `id`, `action`, `sources`, `copies`, `edits`, `status`; each `left_in_place`, `questions`, and `could_not` entry keeping only `source` (an entry with no `source` is dropped). A re-check (`R` > 0): only the units being fixed, and the three lists empty.
5. **The open run's `fixing`** lists the unit ids the current round checks: every unit handed on round 0, the fixed units on a re-check. `record` sets it; `findings` reads it. `null` outside the batch cycle.
6. **`record --failed`** is run after the migrator failed for good (spec 04 item 22, "When a part fails").
   - With a valid record, units are sorted (spec-migration-verifier.md 07 item 3). A unit's writes are: each `copies` line present in its note, each `edits` `after` present, and, for a `reject` unit, each source line gone from where it sat. All present: **whole**. None present: **not started**. Otherwise: **partly written**. Whole units go on as in item 1, with `fixing` set to them. The rest are undone (item 10). With no whole units, the run moves to the next batch. A unit `record` would refuse under item 14 or item 15 is sorted as not whole, whatever of it is written.
   - With a missing or invalid record on round 0: the batch has no units. An invalid record file is moved out of `.runs/units/` to `.runs/{run-id}/record-b{N}-invalid.json`, so `.runs/units/` only ever holds valid records, the ones the Edit guard is handed (spec-edit-guard.md 11 item 21). The step becomes `batch-failed`, and `next_check` is the next flags file number for the run (1 if none was awaited before).
   - With a missing or invalid record on a fix round: the last valid copy is put back as the record file, and every unit in `fixing` is undone from it. Units already approved stand.
7. **`findings`** (needs `verifying` and the findings file) checks the file (spec-migration-verifier.md 05.1 item 2, 05.2): `batch` is `b{N}`, `round` is `R`; `units` holds exactly the ids in `fixing`, once each, each with `verdict` `approve` (no problems) or `fix` (at least one problem); each problem has `check` (`lost-detail`, `status`, `scope`, `standalone`), `note`, `line`, and `what`; `missed` is a list whose entries have `source` and `what`, and is empty on a re-check. A refused file: exit 1 with one line; nothing changes.
8. **What `findings` does with a valid file.**
   - `approve`: the unit joins the unit index, `{"run", "unit": "b{N}-u{K}", "state": "approved", "pointed_lines": []}`.
   - `fix` with `R` < 2: the run goes back to `migrating`, `round` R+1, and `fixing` is the units to fix.
   - `fix` with `R` = 2: the unit is undone (item 10).
   - When no unit is left to fix: `batch` + 1, `round` 0, `fixing` null, step `migrating`; after the last batch, step `batches-done` and `batch` stays at the last.
9. **`findings --failed`** (needs `verifying`): every unit in `fixing` is undone. Units approved in earlier rounds stand. Then the run moves on as in item 8's last bullet.
10. **Undoing a unit** (spec 09.1 items 2, 4, 5, 6), from its last valid record copy, never the snapshot. Pointers don't exist yet in this milestone; their undo is Milestone 10.
    - Each `copies` line is removed from its note. Among identical lines, the one removed is one the snapshot doesn't hold, counting repeats (spec 08.1 item 1).
    - Each `edits` entry's `after` goes back to `before`. When the edited line carries a pointer `pointers` wrote since, for a `migrate` unit with the same source line (5.4 item 9), undo finds it as `after` with that pointer's destinations added (and its `[?]` gone, if the pointer took it), and writes `before` with those destinations kept at its end, as 5.4 items 4 to 6 write them. Every other unit of this run whose `pointed_lines` holds the line's old text gets its new text. Added 2026-10-14. The migrate unit is then undone as item 13 says.
    - A `reject` unit's source line goes back under the nearest non-blank line that sat above it in the snapshot.
    - A created note (`creates_note` true) left holding only blank lines and frontmatter moves to `.runs/{run-id}/removed/{its path}`.
    - A line undo can't find is left alone and saved for the run log in `.runs/{run-id}/undo-misses.json`, a list of `{"unit", "note", "text"}`.
    - **Undo removes whatever of the unit exists, across its record versions** (spec 09.1 item 3). After undoing from the last valid copy, undo goes back through the unit's earlier saved copies (`record-b{N}-r{R}.json`, newest first) and undoes any of their writes still in the notes: a copy line the note holds that the snapshot can't account for, or an edit whose `after` is still there. A miss is a line the unit wrote that undo can't find. Lines a partly written or not-started unit never wrote aren't misses, and nor are an earlier copy's lines that are already gone. When undo runs and misses nothing, `undo-misses.json` is written as `[]`. On a fix round, `record --failed` sorts only the units in `fixing`; approved units are neither sorted nor undone. So a fix round whose migrator rewrote the record, then failed before rewriting the note, leaves nothing of the unit behind.
    - The unit joins the unit index as `undone`, `pointed_lines` `[]`. Undone units' last problems are kept for the run log: the findings files already hold them.
11. **Each note is written whole** (spec 08.1 item 2), with `lines.write_note_whole`.
12. `status` text: at `verifying`, "run the migration-verifier on batch {N}, round {R}, save its findings, then findings"; at `batches-done`, "pointers"; at `batch-failed`, "run editguard check for flags-{n}.json, then act".
13. **An undone edit takes the migrate unit on its line with it** (added 2026-10-14, the writer's ruling). When a unit of this run with an `edits` entry is undone, for any reason, every `migrate` unit of this run whose source line that entry changed is undone too: its copies removed and its pointer taken off (5.5 item 6), so the line reads `before` again. A copy carrying a change the writer didn't keep, such as a status tag never given, is over-promotion; the next run retries the line on its own (spec 11 item 81), so nothing is lost.
    - "Changed that line": same note, and the entry's `before` is the source text, at the same snapshot line when both texts are in the snapshot, or a later text in the source line's chain of the run's edits (5.4 item 9). A migrate unit whose source is any other line stands.
    - Applied at the end of each command that undoes units: `findings` and `findings --failed`, `record --failed`, `act` at `pointed` and at `judged`, and inside `pointers` after its misses are undone. Repeated until nothing more is undone, since a migrate unit can carry edits of its own. Only units the unit index lists `approved` or `pointer-written` are undone; a migrate unit that joins the index later, after its edit was undone, is caught by the next of these commands. `recover` undoes every unit anyway.
    - The reason saved for the run log is `{"why": "edit-undone", "unit": "{the edit's unit}"}`. In `act`, a flag naming a unit this undoes is skipped like any unit undone in that step (5.5 item 2, last bullet). Undo's misses go to `undo-misses.json` as usual.
    - At `close`, both units are undone, so their lines stay off the handled list, and every comment in their piece with them (5.6 item 3); the next run hands the piece back.
    - **Edits built on an undone edit come out first** (added 2026-10-14, the writer's ruling). A unit whose `edits` entry has, in the same note, a `before` equal to an undone unit's `after` built on that edit. Before a unit is undone, every unit of this run the unit index lists approved or pointer-written that built on it is undone, and each of those first undoes the ones built on it, so the chain comes undone newest first and undo finds each `after` where it expects it. Each such unit's reason is `{"why": "chain-undone", "unit": "{the unit it built on}"}`. Then the migrate units whose source line any undone edit in the chain changed are undone as this item says. The line ends at the text before the first undone edit, with any pointer of a unit still standing kept (item 10). Units undone together (`findings --failed`, `record --failed`, round-2 failures in one `findings`, `recover`'s units not yet in the index) are taken in that order too: a unit that built on another goes first, whatever the record order. In `record --failed`, an edit's `after` counts as written when a later edit of the units being sorted built on it and that later `after` is there.
    - **Where the check runs, so the two meet whenever they do** (added 2026-10-14). `findings` puts its approved units in the unit index before it undoes any unit, and ends with the check above. Every unit is approved only at `findings`, and every undone unit joins the index, so the check sees each pair as soon as both are in it: a migrate unit still waiting on its batch's check when its edit is undone is undone when it is approved and joins the index; so is a migrate unit in a later batch whose source line an earlier batch's undone edit changed. After `pointers`, `act` runs the check after its undos.
14. **A `migrate` source recorded as an edit left it is a record error** (added 2026-10-14, the writer's ruling). A source's `text` is the line as it read when the run started (spec-migrator.md 05.2). When a `migrate` unit `record` checks has a source text that isn't a line of the note's snapshot and is the `after` of an `edits` entry in the same note, in this record or an earlier batch's record of this run, `record` refuses with one line: "The record file {path} was refused: unit {id}'s source in {note} is the line as an edit left it; its text must be the line as it read when the run started." Nothing changes, so the skill's retry sends the migrator back, as for item 1's copy refusal.
    - **In `record --failed`** (added 2026-10-14, the writer's ruling), such a unit is sorted as not whole and undone, like any unit a failed migrator didn't finish (item 6), with the reason `migrator-stopped`. The rest of the record is sorted as before. The next run retries its line (spec 11 item 81).
15. **A `migrate` copy into a note its source line's pointer already names is a record error when an earlier run already sent that line to that note for the same trigger** (added 2026-10-23, spec 11 item 95, narrowed by item 99). The pointer is the one on the source's `text` as the record holds it, the line as it read when the run started, so only earlier runs' pointers count; its destinations are read as 5.2 item 7 says. Only `migrate` units are checked: `reject` and `edit` units get no pointer (spec 08.2 item 1), so their copies pass wherever they go. The copy's words don't matter.
    - **The earlier unit** is a `migrate` unit in an earlier run's record in `.runs/units/` (any file not named for this run), that the unit index lists `pointer-written` for its run, with a source in the same note whose text is the same line and a copy into the same note. The earlier source's text is the line before its pointer, and this run's carries the pointer, so both are compared with the pointer and any `[?]` taken off (`undo.bare`).
    - **The same trigger:** the same `kind`. For `comment`, one comment in the source line's piece holds both units' trigger `text` as a substring, the matching of 5.6 item 6's keep lines (spec 11 item 97), over the same comments: the piece's comment lines in this run's `batches.json`. For `tag` and `request`, the trigger texts are the same.
    - **A copy the earlier units can't account for passes:** no earlier unit sent the line there, or one did for another trigger (case 104: a tag; case 186: another comment), or its trigger is in no comment of the piece, so it can't be matched (case 187). The migrator's fifth instruction still stands, and a refused ask would fail without a word (spec 11 item 99).
    - **Renames are followed** (added 2026-10-25, spec 07.1 item 13; spec 11 item 104). The earlier unit's source and copy notes are read through every rename found since its run, in order: the `renamed` of each history entry after its run's, then this run's `batches.json` `renamed`, which no history entry holds yet. So an earlier copy into `Ideas/idea-almond.md` counts as a copy into `Ideas/idea-almond-renamed.md`, the copy's note as this run's record names it, however many runs back the rename was.
    - `record` refuses with one line naming the unit, the source line and its note, and the copy's note: "The record file {path} was refused: unit {id} copies `{source text}` in {note} into {copy note}, which that line's pointer already names; take that copy out of the note and the record." Nothing changes, so the skill's retry sends the migrator back.
    - **In `record --failed`**, which runs no refusals, such a unit, found by the same rule, is sorted as not whole and undone, with the reason `migrator-stopped`, though every line it recorded may be in its notes (spec 11 items 90, 95, 99). The rest of the record is sorted as before. The next run retries its line.

### 5.4 Pointers (Milestone 10)

Spec: spec-run-manager.md 04 items 6, 15, 22; 05 item 1; 08.1; 08.2; 08.3. spec-edit-guard.md 03.1 item 2, 03.2 item 4, 03.3 item 2, 04 (`pointer-mismatch`). guide-metadata-and-markup.md 13 (vault path `Projects/Script Asst/guides/`).

| Command | Arguments |
| --- | --- |
| `pointers` | `--project P` |

1. **`pointers`** needs `batches-done`. It writes every pointer for the run's approved `migrate` units, then moves the run to `pointed` with `next_check` the next flags file number (one past the highest `flags-*.json` in the run folder, or 1). A unit is approved when the unit index lists it `approved` for this run. Its record is its batch's record file in `.runs/units/`.
2. **Which lines.** Each `sources` line of each approved `migrate` unit, found in its note by exact text, or by the texts item 9 adds when this run edited it. Among identical lines, the snapshot says which one: the occurrence at the same place among repeats, counting from the top (spec 08.1 item 1). `reject` and `edit` units get no pointer (spec 08.2 item 1).
3. **The destinations** are the distinct `copies` notes of the unit, in record order. Each is written as `[[Projects/{project folder name}/{path without .md}|{file name without .md}]]`, as research link lines are (section 1 item 5).
4. **The form** (spec 08.2 item 2): ` [migrated-to:: {link}, {link}]` appended at the very end of the line, after any tag, one space before it. Nothing else on the line changes.
5. **A line that already has a pointer** (spec 08.2 item 3), from an earlier run or from another unit in this run: the new destinations join it, inside the same brackets, after the ones there, separated by `, `. A destination already listed isn't added again.
6. **A `- [?]` line** (spec 08.2 item 4): writing its pointer also turns `- [?]` into `- `. Only the checkbox goes; the indent and the rest stay.
7. **Units are taken in unit index order.** Several units can point from one line; each adds its own destinations.
8. **The unit index** (spec 04 item 15): each unit that got its pointers becomes `pointer-written`, and `pointed_lines` holds each source line's text as it reads after its pointer was written, one per source line, in `sources` order. A line that a later unit changes again keeps, in the earlier unit's entry, the text it had right after that unit's pointer.
9. **A source line `pointers` can't find** (the writer changed it after the run started): no pointer is written for that unit, the unit is undone as Milestone 9's undo does, and the line is saved for the run log in `.runs/{run-id}/pointer-misses.json`, a list of `{"unit", "note", "text"}`.
   - **The run's own edits don't count as a change** (added 2026-10-14, from the live run where an approved `edit` unit tagged the line an approved `migrate` unit moved, and the migrate unit was undone). When an `edits` entry of a unit of this run that the unit index doesn't list `undone` (an `edit` unit or any other) has the source line's note and `before` equal to its text, the line is looked for by that entry's `after` too. Edits are followed as a chain: an entry whose `before` is an earlier entry's `after` adds its own `after`. The pointer goes at the end of the line as it reads, after any tag the edit added (item 4). `pointed_lines` holds that text (item 8).
   - The edits that count are read again after each unit `pointers` undoes, so an edit undone here no longer does, and the migrate units on its line are undone with it (5.3 item 13).
   - Only a change the run didn't make still undoes the unit: a line that reads neither the source text nor any `after` in its chain, such as the writer's rewording on top of the run's edit.
   - The same reading finds the line wherever a source line is looked for after `pointers`: taking a pointer off (5.5 item 6), rewriting one (5.5 item 7), and the handled list at `close` (5.6 item 3). There, the edits of units already undone don't count, since undo put their `before` back.
10. **Each note is written whole**, once, after all its pointers are in.
11. **Done check for each case:** the real `editguard` (the runner's `editguard` step) gives no `pointer-mismatch` and no `copy-mismatch` flag after `pointers`. A case puts the expected `flags-1.json` in `expected/tree/` to check this.
    - **The Edit guard on a line the run edited, then pointed** (added 2026-10-14, item 9). The line now reads an `edits` entry's `after` with a Run manager pointer added. With the pointer stripped (spec-edit-guard.md 03.1 item 2), the entry explains the line, and the pointer counts as a Run manager edit when a `migrate` unit that isn't undone has that source line (03.2 item 4); without such a unit it is a lookalike and the line is `unexplained-change`. The edit's flags (`writer-line-edited`, `brain-dump-status-tag`, and the rest) hold the entry's own `after`, without the pointer, so they read as they would with no pointer. `pointer-mismatch` checks the edited line's destinations as it checks an unchanged line's, and flags a pointer-written unit's edited source line that carries none.
    - **A line two or more of the run's edits changed in turn** (added 2026-10-14, the writer's ruling). When `edits` entries of units that aren't undone run from the snapshot line to the line now (each `before` the last one's `after`), with or without a Run manager pointer on the end as above, the chain explains the line. Each entry is its own change for the markup rules, with its own `before` and `after`, named by its own unit: `writer-line-edited` on each, `brain-dump-status-tag` on the one that added the tag. A flag judged not asked for undoes the unit it names, and 5.3 item 13 takes the units built on it with it. A chain with a link missing from the records is `unexplained-change`.
12. `status` text at `pointed`: "run editguard check for flags-{n}.json, then act".
13. **Taking a pointer off again** (spec 09.1 item 2, last bullet) is built in Milestone 11, where `act` and `recover` first need it.

### 5.5 Migration flags (Milestone 11, round 1)

Spec: spec-run-manager.md 04 item 22; 05 items 3, 6, 7; 08.2; 08.5; 09.1. spec-migration-verifier.md 02 item 3; 03.2; 04.3; 05.3; 06 items 5, 6; 07 items 1, 2. spec-edit-guard.md 05; 06 item 1; 07.

1. **The open run gains `first_check`**, set by `pointers` to the flags number it waits for. It is the flags file the migration-verifier judges, and the runner's second Edit guard check passes it as `--judged` (section 2). `null` before `pointers`.
2. **`act` at `pointed`** (the awaited flags file exists):
   - `copy-mismatch`: the unit it names is undone, pointer included (item 6).
   - `pointer-mismatch`: the line's pointer is rewritten from the records (item 7). The migration stays.

The change stands, and the flag stays out of `verify-flags.json`. Still sent to the call: a flag that names no unit, a flag on a unit whose `trigger` kind is `tag`, and every flag on a line two or more of the run's units edited in turn.

A migrate unit's pointer on the line is no `edits` entry, so it doesn't count.
     - **Each flag that stood becomes an `asked` entry**, `{"flag": id, "verdict": "asked", "asked_by": {"kind": trigger kind, "note": "", "line": null, "text": trigger text}}`, so the second check drops it as it drops a flag judged asked for (spec-edit-guard.md 07 item 2; plan-run-manager.md 06 item 13). The trigger records no note or line, hence `""` and `null`; the run log finds the comment itself (5.6 item 6). With other flags left, the entries wait in `.runs/{run-id}/stood-flags.json` until `findings` (item 4). With none left, `act` writes them as `findings-flags.json` itself, so the second check is handed `--judged` (plan-run-manager.md 06 item 14 (2)).

   - The open run's `edited` becomes `true` if `act` changed any note. At `acted`, `next_check` is one more than the flags file just read when `edited` is true, else `null`.
   - A flag naming a unit already undone in this step is skipped.
3. **`verify-flags.json`** (spec-migration-verifier.md 03.2): `{"flags": [the flags, as the Edit guard wrote them], "units": {"b1-u2": {cut-down unit}, …}}`, one cut-down unit (the fields of 5.3 item 4) for each unit a flag names, read from its batch's record file. The skill hands this file to the migration-verifier with the typed request, the project folder, and the rules path.
4. **`findings` at `judging`** (needs `findings-flags.json`) checks it (spec-migration-verifier.md 05.3): `flags` holds exactly the flag ids in `verify-flags.json`, once each; `verdict` is `asked` or `not-asked`; an `asked` verdict has `asked_by` with `kind` `comment` or `request`, and `note`, `line`, `text` (for a request, `note` and `line` are `""` and `null`); a `not-asked` verdict has `asked_by` `null`. A refused file: exit 1, nothing changes. Valid: the entries in `stood-flags.json` (item 2), if any, are added after the verdicts, and the step is `judged`. The check runs first, so the migration-verifier's file still holds exactly the `verify-flags.json` ids (plan-run-manager.md 06 item 14 (2)). **`findings --failed` at `judging`**: writes `findings-flags.json` itself with every flag handed to the call `not-asked` (spec-migration-verifier.md 07 item 2), then the `stood-flags.json` entries, since a flag that stood still stands (plan-run-manager.md 06 item 14 (3)), and moves to `judged`, so the second check reads the same file. The original refused file, if any, is kept as `findings-flags-refused.json`.
5. **`act` at `judged`** (spec-edit-guard.md 06 item 1) acts on the flags in `verify-flags.json` only. An entry for a flag that stood (item 2) holds no flag that file holds, so it changes nothing here:
   - `asked`: nothing changes. The run log will name the comment or request.
   - `not-asked`, flag names a unit: the unit is undone, pointer included. Several flags on one unit undo it once.
   - `not-asked`, no unit: the line is restored (spec 08.5): a changed line goes back to `before`; an added line is removed; a removed line goes back under the nearest non-blank line above it in the snapshot. A line a restore can't find is left alone and saved in `.runs/{run-id}/restore-misses.json`, a list of `{"note", "before", "after"}`, for the log's Other notes. A `fingerprint-changed` note can't be restored; nothing changes and the log names it.
   - Then step `acted`, with `next_check` one more than the first check when this `act` or the one at `pointed` changed a note, else `null`.
6. **Undoing a unit with a pointer** (spec 09.1 item 2, last bullet): for each pointed source line, found as 5.4 item 9 says (the unit's own edits still count, since its pointer comes off first), the unit's destinations come off the pointer, unless the snapshot line already named them or another unit of this run that isn't undone still points there. A pointer left with no destination is removed with the space before it. If the snapshot line was `- [?]` and no destination this run added is left on it, `[?]` goes back. The unit index entry becomes `undone`, `pointed_lines` `[]`. Every other unit whose `pointed_lines` holds that line's old text gets its new text, so `pointed_lines` always matches the note. Everything else is 5.3 item 10's undo.
7. **Rewriting a pointer** (spec 05 item 6), the line found as 5.4 item 9 says: the line's destinations become the ones its snapshot line named, then those of every `pointer-written` unit of this run that points from it, in unit index order, each once. `pointed_lines` of each such unit is updated to the line's new text.
8. **`act` at `batch-failed`** (the awaited flags file exists; spec 07.2 item 4): every `unexplained-change` flag is restored as in item 5's no-unit bullet. Other flags are ignored here; the run's real check after `pointers` sees them again. Then the run moves to the next batch, or `batches-done` after the last, with `next_check` `null`.
9. **Second-check flags go to the run log, never back to `act`** (spec-edit-guard.md 07 item 3). `close` handles them (round 2).
10. `status` text: at `judging`, "run the migration-verifier on verify-flags.json, save its findings as findings-flags.json, then findings"; at `judged`, "act"; at `acted`, as for research.

### 5.6 Close and recover (Milestone 11, round 2)

Spec: spec-run-manager.md 04 items 8, 17, 20, 22; 05 item 7; 07.1; 07.3; 09.2 items 2, 3, 5. spec-migrator.md 06. spec-edit-guard.md 07. Round 1 (5.5) is built first; these cases run its commands to reach `acted`.

1. **`close` on a migration run** needs `acted`, and the awaited flags file when `next_check` is set. In order: it reads the second check's flags, builds the handled entries, writes the run log, adds the history entry, clears the open run, and prunes snapshots, as on a research run.
2. **Second-check flags** (spec-edit-guard.md 07): the Edit guard already drops flags judged asked for, and flags that stood on an approved unit (5.5 item 2). Every flag left goes under "Other notes" as still flagged, quoted with its rule and note, except one with the same rule and note as a first-check `fingerprint-changed` flag, which is already named. `close` never acts on them.
3. **What goes on the handled list** (spec 07.1). Each entry is spec 04 item 20's shape, `run` this run's id, `text` the line as it reads in the note at `close`, and `pointer` the destinations on that line, or `null`. A unit counts when the unit index lists it `approved` or `pointer-written` for this run. A source line the run edited is found by the counted units' edits, as 5.4 item 9 says, so a migrated line the run also tagged goes on once, as `migrated`, with its tag and pointer in `text`.
   - Each source line of a counted `migrate` unit: `migrated`.
   - Each line of a counted `reject` unit's copies that is a trigger line (5.2 items 2 and 3): the moved line is `rejected`; the reason comment below it is `written`.
   - Each trigger line in a counted `migrate` or `edit` unit's copies: `written`.
   - Each `edits` `after` line of a counted unit, and each source line of a counted `edit` unit still in its note: `edited`.
   - Each `left_in_place` and `questions` source line of a batch whose record was used: `left in place`. A `missed` line never goes on (spec 11 item 81).
   - Each comment line in `batches.json` of a batch that didn't fail and that the record accounts for: `comment` (spec 11 item 74), except every comment in a piece (`batches.json`) holding a source line of an undone unit, a `missed` line, or a line a `could_not` entry names, which stays off so the next run hands that piece to the migrator again (spec 11 items 81 and 107).
   - **The record accounts for a comment** (added 2026-10-25, spec 07.1 item 15; spec 11 item 106) when a unit of the run's records, its `trigger` kind `comment` or `request`, holds a `trigger` `text` that is a substring of the comment, as the keep lines match (item 6); or when the snapshot line directly above the comment is a bullet that a unit's source or `edits` `before`, a `left_in_place`, `questions`, `missed`, or `could_not` source names (note and text); or, for a comment not directly under a bullet, on its own in its piece, when any of those names a line in the same piece. A comment it doesn't account for stays off and the log lists it under Other notes with the lines the run did nothing with, outer indent stripped. A comment in a piece that stays off is listed only when the record doesn't account for it, so a comment under a `missed` or `could_not` line isn't (spec 11 items 81 and 107).
   - **A `could_not` entry** (added 2026-10-25, spec 07.1 item 14; spec 11 item 105): one that names a line keeps only that line off, and the rest of its story note goes on as usual; that line isn't listed with the lines the run did nothing with. One that names a story note and no line (5.3 item 2) keeps every line of that note off and out of that list.
   - Never: lines of undone units, a line a `could_not` entry names, every line in a note a `could_not` entry names with no line, lines of a `batch-failed` batch, and any tagged batch line none of the above names (spec 07.1 item 8), which the log lists under Other notes.
   - Never: a request comment `close` writes (item 10). It is written after the handled list is built, so nothing names it, and the next scan finds it as a trigger line (spec 07.1 item 3; spec 11 item 96). A request comment an earlier run wrote is a comment like any other: it goes on as `comment` when its batch and piece let it (the bullet above).
   - A source line shared by a counted unit and an undone unit stays off, so the next run retries the undone unit; the migrator's instruction 5 keeps the counted unit's copy from being written twice (spec 11 item 83, superseding item 79). The counted unit's copies still go on as `written`.
   - A line counted twice (two units from one source line) gets one entry. A line no longer in its note gets none. A missed line or an edit's `after` line may not be a trigger line; it still goes on, which is harmless, since the scan only ever matches trigger lines.
   - **Order:** new entries go after the existing ones, sorted by note path (Python string order), then by their place in the note at `close`. A skipped pointer line's entry changes only its `text`.
4. **Skipped pointer lines** (`batches.json` `skipped`, spec 07.1 item 4): the handled entry whose text is the `was` and whose note matches gets the line's text at `close`.
   - **Carried-over entries** (added 2026-10-25, spec 04 item 20; 07.1 item 13; spec 11 item 104): each entry in `carried.json` (5.2 item 16) whose `text` still reads `was` gets `text` the line as it reads at close, found as a source line is (5.4 item 9) or, for a comment, as the comment bullet above finds it; `note` the line's note; and `pointer` the destinations on that line, or `null`. It keeps its place, `outcome`, and `run`. Entries the scan didn't match are left as they are. A recovering run's `close` changes no entry (spec 07.1 item 13).
5. **The history entry** (spec 04 item 17): `id`, `kind` `"migration"`, `run_number` `null`, `started`, `ended`, `how`. No `failed` key. A closed run's entry also holds `renamed`, copied from its `batches.json`, `[]` when empty, so `record` can follow a story note through every rename since an earlier unit (5.3 item 15). A recovered run's entry has none: it carried nothing over (added 2026-10-25).
6. **The run log** (spec 07.3; spec 11 item 81). Headings, fixed, in this order: `## Questions for you`, `## Migrated`, `## Rejected`, `## Other edits you asked for`, `## Left in place, and why`, `## Could not do`, `## Units undone`, `## Lines the checker says were missed`, `## Changes put back`, `## Other notes`. The first line is "Migration run, started {started}." The typed request, when there is one, is the next line: `Your request: "{request}"`. "Nothing needs you." follows when there are no questions. Source lines are quoted in code marks. Under Questions for you, the answer line is exactly "Answer with a comment on the source line, then start another migration run." Under Units undone and Lines the checker says were missed, each entry ends with exactly "The next migration run tries this again." instead. Directly above that line, each entry may hold, each as its own sub-bullet (added 2026-10-23, spec 11 items 93, 96, 97):
    - **Keep lines**, "Keep your comment `{comment}` until this migrates.", one per comment, in note order. An undone unit gets them when its record's `trigger` kind is `comment`: the one comment in its source lines' pieces whose text holds the trigger's `text` as a substring, or every comment in those pieces when none or more than one does. A missed line gets them when it carries no status tag: every comment in its piece. The comments are the piece's comment lines in `batches.json`, the ones handed to the migrator, so a comment already on the handled list is never named. The comment is quoted whole, `%%` marks included, with its outer indent stripped. A unit or line its own tag triggered gets none.
    - **The request sentence**, "The run wrote your request as a comment under this line: `{source line}`. Keep it until this migrates.", once per source line that has the request comment under it at close (item 10), whether written now or already there from an earlier run. An undone unit whose `trigger` kind is `request` gets it in place of keep lines. A missed line with no status tag, in a run with a typed request, gets its keep lines first, then the request sentence. A source line `close` can't find gets no comment and no sentence.
    - With no questions, the log still opens with "Nothing needs you.": neither line asks the writer to do anything (spec 11 item 93). Destinations are links in the form of section 1 item 5. Why a unit was undone is one of: "the migration-verifier still found problems after 2 fix rounds:" with each problem nested as `{check}: {what}`; "its copy didn't match its record"; "a change it made wasn't asked for:" with the flag's rule and line; "the migrator stopped before writing it whole"; "the migration-verifier couldn't check it"; "its source line changed before its pointer was written"; "the run's edit to this line was undone, so the copy made from the edited line came out too" (5.3 item 13); "it changed a line the run had already edited, and that earlier edit was undone" (5.3 item 13, chain). Under Other edits you asked for, a flag judged asked for whose unit was undone anyway is left out (added 2026-10-14). A flag that stood on its approved unit (5.5 item 2) is named in the same words as one judged asked for (added 2026-10-23, spec 11 item 101; plan-run-manager.md 06 item 14 (1)): an `asked` entry whose flag `verify-flags.json` doesn't hold is read from its unit's `trigger`. A `request` reads "as your typed request asked." A `comment` reads "as your comment `{comment}` in {note link} asked.", the comment being the one in the unit's source lines' pieces whose text holds the trigger's `text`, found as the keep lines find it, quoted whole with its outer indent stripped. When no single comment holds it, the trigger's `text` is quoted, with no note. Undo, pointer, and restore misses, notes changed outside the run (`fingerprint-changed`), skipped pointer lines, lines the run did nothing with (comments included, item 3), and second-check flags go under Other notes, one bullet each, saying what happened in one plain sentence. Each rename in `batches.json` gets one, after the lines the run did nothing with: "`{from}` looks renamed to `{to}`. Its {N} handled lines carried over.", N the entries item 4 moved from `from` to `to`, "line" for 1 (added 2026-10-25, spec 07.3 item 2 entry 10). Under Could not do, an entry with a source naming no line reads "{note link}: {what}".
7. **`recover` on a migration run** (spec 09.2 item 3) replaces the refusal "Recover for migration runs isn't built yet." It refuses a run with `recover_tried`, and saves `"recover_tried": true` before its undo edits any note, as on a research run (section 4 item 4; spec 09.2 item 6; added 2026-10-26). At any migration step, it undoes every unit of the crashed run not already undone, newest first (last batch first, then record order reversed), each from its last valid record copy, pointer included. Nothing goes on the handled list. When the crashed run had a typed request, recover's `close` writes the request comment (item 10) under each source line of every unit of the crashed run whose `trigger` kind is `request`, each unit read from its batch's last valid record (`recover.request_sources`); a unit its tag or a comment started gets none (spec 11 item 96). Then the open run gets `"recovering": true`, step `recovered`, `next_check` the next flags number, and `first_check` `null`, so the recover check is a first check: nothing judged before the crash is dropped from it. The session runs the Edit guard; then `act` at `recovered` restores every `unexplained-change` flag as 5.5 item 8 does and names the rest, step `acted`, `next_check` `null`; then `close`.
8. **The recover log** is `run-YYYY-MM-DD-HHmm-recover.md` (time of `recover`). First line: "Recover run, for {crashed run id}." Then: "Every unit of the crashed run was undone. The next migration run does that work again." Then "Nothing needs you." when Changes put back is empty, as on a research recover log (section 4 item 16). Sections, each left out when empty: `## Changes put back`, `## Other notes` (undo and restore misses, notes changed outside the run, and "Markup wasn't checked on the first try." when the crashed run was waiting for a flags file that never appeared, as on a research recover). In `recover`, units already in the unit index become `undone` in place; units not yet in it join at the end, in undo order. **The run state is saved after each unit it undoes** (added 2026-10-26, spec 11 item 119), with that unit `undone` and its misses added to `undo-misses.json`, so a recover that crashes on a later unit leaves the unit index naming every unit already undone, and the abandon log lists only the rest (section 6 item 5). Its history entry is the crashed run's, with `how` `"recovered"`. The recover log says nothing about the request comments its `close` wrote (item 7): it has no Units undone section, and the spec doesn't say where such a line goes.
9. `status` at `recovered`: "run editguard check for flags-{n}.json, then act".
10. **The request comment** (added 2026-10-23, spec 11 item 96, Claude's readings approved in item 97 and the coordinator's readings of 2026-10-23). With a typed request, `close` writes `{indent}    %% [AGENT] Your request from the migration run of {date}, for this line: "{request}" %%` under each source line of an undone unit whose `trigger` kind is `request` (whatever undid it, a flag judged not asked for included) and under each missed line with no status tag. On a recovering run, item 7 says which lines.
    - `{indent}` is the source line's indent; the comment sits four spaces deeper, as a research link line does (section 1 item 5). `{date}` is the run's start date, `YYYY-MM-DD`. `{request}` is the open run's `request`, word for word.
    - It goes on the line directly under the source line, above any comment already there (spec 08.4 item 1). The source line is found as the handled list finds it (5.4 item 9).
    - Where the identical line already sits among the comments directly under the source line, it isn't written again. The log's request sentence (item 6) is still given.
    - It is written after the handled list is built and after the last Edit guard check, so no check flags it and it stays off the handled list (item 3). Each note is written whole, once (spec 08.1 item 2).

## 6. Abandon and the stop

Added 2026-10-26 for plan-run-manager.md Milestone 18. Spec: spec-run-manager.md 04 items 16 to 18 and 22; 09.2 item 6; 09.3; 09.4; 11 items 108 to 115, 119, and 120. The one try is in section 4 item 4 and 5.6 item 7.

Exact messages and log lines in quotes come from the spec, except "There is no open run to abandon." and the abandon log's own entry sentences. Everything else here the spec doesn't say is Claude's reading, made in the build on 2026-10-26, and goes to the writer as section 4's readings do (spec 11 item 121).

1. **`abandon`** (`abandon.py`) works on either run kind. With no open run it exits 1 with "There is no open run to abandon." With an open run that has no `recover_tried`, it exits 1 with "Run /script-asst:run recover first." (spec 09.3 item 1). Any recover counts, one that worked included: a recover that worked can still leave a run stuck, such as an Edit guard that never writes its flags file.
2. **It edits no note** (spec 09.3 item 2): no undo, no request comment, no handled entry, no change to the unit index or to any file in the run folder. It adds the history entry, `how` `"abandoned"`, `ended` the time `abandon` runs, no `renamed`, and `failed` `[]` on a research run only, then clears the open run. It prunes no snapshot: the run's folder and snapshot stay until a later `close` prunes as usual (spec 09.3 item 5).
3. **The log** is `Runs/run-YYYY-MM-DD-HHmm-abandon.md`, timed when `abandon` runs, `type: [run-log]`. First line "Abandoned run, for {run id}.", then "This run was closed without its last checks. Below is what was never checked." Then the sections, each left out when empty, as `## ` headings: `## Copies still in your notes`, `## Your request`, `## Never checked`, `## Other notes`. Other notes always holds the snapshot folder, so the log always has one section.
4. **A log it can't write** (spec 09.3 item 3): the log is written first. If writing it raises an OS error, the run still closes, `abandon` exits 0, and stdout holds one line saying the log couldn't be written, then the log's whole text, frontmatter included. When the log is written, stdout is `run log: Runs/{name}` only, so the skill shows the text only when it was printed.
5. **Copies still in your notes** (migration runs; spec 09.3 item 4 section 1; spec 11 items 111 and 119): every unit of the run's batches, 1 to the open run's `batch`, read from each batch's last valid record as `recover` reads them (`recover._batch_units`), that has copies and that the unit index doesn't list `undone` for this run. One bullet per unit: each source line quoted with its note link, then each distinct copy note as a link, and a nested bullet "Delete this copy before the next migration run, or the run copies this line again." A unit with no copies, a pure `edit` unit, isn't listed.
6. **Your request** (migration runs with a typed request; spec 09.3 item 4 section 2; spec 11 item 112): "You typed `{request}`.", then each source line of every unit whose `trigger` kind is `request`, from `recover.request_sources`, whatever the unit index says of it, each quoted with its note link, then "Type your request again on the next migration run." With no such unit, the source lines are left out.
7. **Never checked** (spec 09.3 item 4 section 3; spec 11 item 120):
    - **The awaited flags file** is the one `next_check` names, except at `judging` and `judged`, where `act` already ran on it (5.5 items 2 and 5). When it doesn't exist: "Markup wasn't checked after the run's last edit." When it does, no `act` has run on it, so each of its flags is listed: its rule, its note link, and its `before` and `after` quoted. Earlier flags files had an `act` run on them, or were replaced by recover's own check, so they aren't read.
    - **A research run's link lines and closes:** each request `mark.json` lists as closed, quoted as it reads closed, with its note link and the link to its research note, only when `act-1.json` doesn't exist: once `act` has run on flags-1, the check that reads them, they were checked.
8. **Other notes** (spec 09.3 item 4 section 4): each entry in `undo-misses.json`, its line quoted with its note link, then the snapshot folder, `.runs/{run id}/snapshot/`, in code marks. Restore misses and pointer misses aren't listed: the spec names undo's misses only.
9. **`mark --stopped`** (`research.mark_stopped`; spec 09.4 items 2 and 3; spec 04 item 18) needs a research run at `started`, refusing as `mark` does otherwise. It edits no note. It takes the missing-outcomes path (section 4 item 1): an `outcomes.json` the session saved anyway moves to `outcomes-refused.json`, `outcomes.json` is written as `[]`, and `mark.json` holds `outcomes_refused` "You stopped this run." and `stopped` `true`. The open run gets `"stopped": true` and moves to `marked`, `next_check` 1. The Edit guard, `act`, and `close` run as usual. `recover` on a stopped run keeps the saved reason, since `mark` reads `mark.json` first (section 4 item 3).
10. **A stopped run's log** (spec 06.1 item 2; 09.4 items 3 and 4; spec 11 item 115): Requests still open opens with "You stopped this run. Every request stays open.", then lists every request as an open request whose outcomes file was refused, each with "You stopped this run." as its one part (section 4 item 20). Each note the first check flagged `unexpected-research-note` is listed once, at the end of the section, under the line "Written before you stopped the run:", as a bulleted note link, and not under Notes changed outside the run. Every other flag is named as on any research run, so a note the run didn't write outside `Research/` stays under Notes changed outside the run. The history entry is `closed`, with `failed` `[]`.
